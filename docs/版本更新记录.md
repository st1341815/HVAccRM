## 二、维护规范（重要）

**每次发版本必须同步做四件事：**

1. 在 `app/__init__.py` 里 bump `__version__`（用 `scripts/bump_version.py <X.Y.Z>`，会同步 `pyproject.toml`）；
2. 在本文件末尾对应的版本系列章节**追加一条记录**，格式见下；
3. 打 **同一个版本号** 的 git tag 并推送：`git tag -a vX.Y.Z -m "…" && git push origin main refs/tags/vX.Y.Z`；
4. 在 GitHub 建 Release，**标题固定为 `HVAccRM vX.Y.Z`**（见下方命名规则）。

```markdown
### vX.Y.Z（YYYY-MM-DD）

- **类型**：feat / fix / style / perf / chore / docs
- **内容**：一句话说明改了什么（功能 / bug / 视觉 / 性能 / 部署 / 文档）
```

### Release 与镜像命名规则（定稿，勿自创）

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| git tag | `vX.Y.Z`（小写 `v` + 严格三段版本号，不带前后缀） | `v1.7.0` |
| **GitHub Release 标题** | **`HVAccRM vX.Y.Z`** —— 前缀固定 `HVAccRM `，后接当前版本号；**不追加主题/形容词** | `HVAccRM v1.7.0` |
| Release 正文 | 主题（如「安全加固版」）写在正文第一行 `## vX.Y.Z · 主题`，不放进标题 | — |
| Docker 镜像 tag | `<DockerHub 用户名>/hvaccrm:X.Y.Z` + `:latest`（打 `vX.Y.Z` tag 后由 Actions 自动发布） | `13uncle/hvaccrm:1.7.0` |
| 本地回滚 tag | `hvaccrm:pre-X.Y.Z`（部署前把上一个线上镜像打上该 tag） | `hvaccrm:pre-1.7.0` |

> **为什么标题不写主题**：Release 列表里标题需要一眼可比（版本号对齐），主题属于「这一版做了什么」，放在正文里更合适；追加形容词会让同一项目的标题长度参差不齐，也不利于按版本号检索/对账。
>
> 一个版本号对应一次「可感知的变更」，不要一个版本号塞多件无关的事；也不要改完代码不 bump 版本号。

## 三、起源：家居建材 CRM（无版本号）

> 项目最早面向「家居建材定制行业（橱柜/衣柜/门窗）」，核心是「房号索引 + 分期收款 + 工序化交付」。
> 以下为 v0.9.0 之前完成的交付，Git 中无版本号。

- **第 1–8 轮完整交付**：楼盘/房号、客户、合同（明细/收款计划/增项）、收款、施工工序、照片、用户/角色/权限、审计、全文搜索（FTS5）等核心模块一次性搭成。
- **NAS 实测修复**：日志、权限、唯一约束修复；自检脚本可重复执行。
- **部署形态迁移**：NAS 部署改为 fnOS Compose 项目形态，补充界面管理入口与路径约定。
- **房号级联修复**：修复房号级联失效与房号静默误选。
- **部署坑记录**：补充 trim-cli 覆盖上传与 .dockerignore 两个部署坑。
- **单元白名单**：单元改为固定下拉（1~9 单元），服务端白名单校验。
- **客户表单增删字段**：新增手机/微信/意向产品，迁移 `0002`。

### v1.7.6（2026-10-30）

- **类型**：fix（微信域名验证失败的真正原因）
- **现象**：v1.7.5 部署后，微信申诉点「验证」仍报 **「访问文本资源失败，请调整后重试」**；但我这边 `curl https://crm.example.com/41abda4e….txt` 返回 200 且内容 40 字节完全一致。
- **根因**：`curl -I`（HEAD）拿到 **405 allow: GET**。FastAPI 的 `@app.get()` **不会**像 Starlette 的 `Route` 那样自动补 HEAD 方法（`APIRoute.__init__` 只取显式传入的 methods），所以只有 GET 被注册。**微信/腾讯云的域名验证器用 HEAD 探测文件存在性**，405 直接被判成「访问文本资源失败」。GET 正常 + HEAD 405 = 典型的「我这边测都通过、平台就是不过」。
- **修法（`main.py`）**：`@app.get(...)` → `@app.api_route(..., methods=["GET", "HEAD"])`，HEAD 与 GET 共用一个 endpoint（不另写逻辑，避免两条路径行为漂移）。
- **自检**：`tests/test_verify_file.py` 增 2 例（路由 methods 必须含 HEAD；HEAD/GET 必须指向同一 endpoint），共 14 例；全量 `pytest` **156 passed**。本地起 uvicorn 实测：`HEAD` → `200 content-length: 40` 且不发 body；`GET` → 200 内容正确；`data/verify/` 通道同样生效。
- **教训（写死）**：**凡是给「外部平台抓取」用的端点，必须 GET + HEAD 双支持并各自实测**。curl 默认发 GET，`-I` 才发 HEAD——只用 GET 自测会漏掉整类问题。以后新增 robots.txt、验证文件、健康检查这类「机器读」的端点，一律检查 HEAD。
- **回滚点**：`hvaccrm:pre-1.7.5`（= v1.7.5 镜像）。

- **修法（`app/static/app.css`，仅桌面端 `@media (min-width:781px)` 块）**：`.date-text` 显式 `white-space: normal` + `word-break: break-all`（恢复 2 行 × 2 字），并把宽度由 `2em` 放宽到 `2.1em`（给 CJK 字形亚像素舍入留约 1px 余量，避免某些字体/缩放下退化成 1 字 1 行）；`跳过原因` 的等宽公式里的 `2em` 同步改为 `2.1em`，保持「跳过原因 = 完工备注 + 施工日期 + 日期控件 + 两处 gap」的对齐关系。

### v1.9.2（2026-10-31）

- **类型**：fix（容器重建后公众号功能失效 —— Chromium profile 锁残留）
- **现象**：v1.9.1 部署后，容器内 `login_state()` 抛 `Chromium 启动超时（CDP 端口无响应）`。v1.9.0 时同样的调用是正常的。
- **根因**（chrome.log 原文）：
  ```
  The profile appears to be in use by another Chromium process (50)

  ```
  `SingletonLock -> d617285a5ae5-50` 里记着**上一个容器的 hostname**。登录态要持久化所以 profile 放在 `/data`（跨容器保留），但锁文件也跟着留下了；容器重建后 hostname 变化 → Chromium 认定 profile 被「另一台机器」占用 → 拒绝启动。

- **验证**：容器内 `rm -f Singleton*` 后 `login_state()` 立即恢复 `{'ok': True, 'logged_in': False, 'qr': True}`；195 tests passed。
- **教训**：**任何把浏览器 profile 放在持久卷的容器化方案，都必须处理 SingletonLock**——否则「第一次能用、重建后失效」这种问题会在最不可预期的时候炸。

- **修复**：**发布改为「逐行 `insertText` + 模拟回车（`Input.dispatchKeyEvent` Enter）」**，这是微信编辑器自己生成段落的方式（产生 `<section><span leaf="">文字</span></section>` 结构），保存后换行 100% 保留。
  - 新增 `wxmp_body.body_lines(case, template)` → 返回纯文本行列表（品牌条/引导语/字段/落款各一行，字段间空行）。

- **回滚点**：`hvaccrm:pre-1.9.5`。

### v1.9.7（2026-10-31，未发 CHANGELOG 的部署中修复）

- **类型**：fix（公众号同步 renderer 僵死 + 图片上传 SSL 握手失败）
- **现象**：v1.9.6 部署后，同步 16 张图的案例时 `Connection timed out`，且「公众号」页面打不开。
- **根因（两层）**：
  1. **Chromium 用 QUIC/HTTP2 与飞牛 Fake-IP 转发层（198.18.0.x + Unbound DNS）不兼容** → 大量 `SSL handshake failed (net_error -100/-101)`。python TLS 100% 成功、Chromium 却大量失败，是典型「中间层对 Chromium TLS 指纹/协议不兼容」。
  2. `_insert_images` 每传一张图都重新 `JS_FOCUS_BODY`（`selectNodeContents` + `collapse`），在已有图时累积渲染问题，加剧 renderer 僵死。
- **修复**：
  - `ensure_browser()` 启动参数加 `--disable-quic --disable-http2`（SSL 失败 1257→32~378，显著缓解）。
  - `_insert_images` 的 `JS_FOCUS_BODY` 移到循环外（只聚焦一次）。
- **⚠️ 未根治**：图片上传时 TLS 层仍有间歇性 SSL 失败（飞牛网络层问题），图多（16 张）时仍可能 renderer 僵死。**这是基础设施问题，非 CRM 代码 bug。** 待飞牛网络层排查。
- **回滚点**：`hvaccrm:pre-1.9.6`。

### v1.9.8（2026-10-31）

- **类型**：fix（图片分批上传，缓解多图 renderer 僵死）
- **方案**：`_insert_images` 改为**分批上传**（每批 6 张，`input[type=file]` 的 multiple 一次传一批），批间延时 3 秒。实测 6~7 张一批能稳定成功，避免一次性 16 张叠加压力导致 renderer 僵死。
- **自检**：195 tests passed。
- **回滚点**：`hvaccrm:pre-1.9.7`。

### v1.9.9（2026-10-31）

- **类型**：fix（renderer 僵死自动检测重启）
- **现象**：用户点击同步仍 `Connection timed out`，之后「公众号」页显示「浏览器异常：Connection timed out」。
- **根因**：`browser_ready()` 只检查 CDP 端口能列 targets，但 renderer 僵死后 browser 进程仍活着、端口仍通，`ensure_browser()` 误判「浏览器可用」而复用僵死实例 → 所有 CDP 调用超时。
- **修复**：新增 `_renderer_alive()`（真实 evaluate `1+1`），`ensure_browser()` 在 `browser_ready()` 为真时再校验 renderer，僵死则 `stop_browser()` + 重启。这样下次操作前自动恢复，不会一直卡在僵死状态。
- **回滚点**：`hvaccrm:pre-1.9.8`。

### v1.9.10（2026-10-31）

- **类型**：fix（找到 renderer 僵死真因 —— `_set_body` 空行 bug 放大空段落）
- **根因（最终定位）**：`_set_body` 的空行逻辑有 bug——遇到空串元素时「当前行空 + 前一行空」会各多按一次回车，导致一个空行被放大成 **6 个空段落**。多段文字（11 行，含 3 个空行被放大）+ 16 张图叠加，微信编辑器 DOM 压力过大 → renderer 僵死。此前「1 行文字 + 16 张图」「11 行文字 + 6 张图」都成功，唯独「11 行文字 + 16 张图」失败，正是这个叠加效应。
- **修复**：
  1. `_set_body` 空行逻辑简化——每个元素间只按一次回车，空串元素 = 一个空段落（只回车不输入），不再放大。
  2. `_insert_images` 改回**逐张 `set_files`**（一次传多张 multiple 反而更容易僵死），每 6 张后延时 3 秒。
- **实测**：`11 行文字 + 16 张图` 完整同步成功（`imgs=16, cdn=16, save_draft ok:true`），renderer 全程健康。
- **回滚点**：`hvaccrm:pre-1.9.9`。

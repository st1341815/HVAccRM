## 二、维护规范（重要）

**每次发版本必须同步做四件事：**

1. 在 `app/__init__.py` 里 bump `__version__`（用 `scripts/bump_version.py <X.Y.Z>`，会同步 `pyproject.toml`）；
2. 在本文件末尾对应的版本系列章节**追加一条记录**，格式见下；
3. 打 **同一个版本号** 的 git tag 并推送：`git tag -a vX.Y.Z -m "…" && git push origin main refs/tags/vX.Y.Z`；
4. 在 GitHub 建 Release，**标题固定为 `HVAccRM vX.Y.Z`**（见下方命名规则）。

```markdown
### vX.Y.Z（YYYY-MM-DD）

- **类型**：feat / fix / style / perf / chore / docs
- **内容**：一句话说明改了什么（功能 / bug / 视觉 / 性能 / 部署 / 文档）
```

### Release 与镜像命名规则（定稿，勿自创）

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| git tag | `vX.Y.Z`（小写 `v` + 严格三段版本号，不带前后缀） | `v1.7.0` |
| **GitHub Release 标题** | **`HVAccRM vX.Y.Z`** —— 前缀固定 `HVAccRM `，后接当前版本号；**不追加主题/形容词** | `HVAccRM v1.7.0` |
| Release 正文 | 主题（如「安全加固版」）写在正文第一行 `## vX.Y.Z · 主题`，不放进标题 | — |
| Docker 镜像 tag | `<DockerHub 用户名>/hvaccrm:X.Y.Z` + `:latest`（打 `vX.Y.Z` tag 后由 Actions 自动发布） | `13uncle/hvaccrm:1.7.0` |
| 本地回滚 tag | `hvaccrm:pre-X.Y.Z`（部署前把上一个线上镜像打上该 tag） | `hvaccrm:pre-1.7.0` |

> **为什么标题不写主题**：Release 列表里标题需要一眼可比（版本号对齐），主题属于「这一版做了什么」，放在正文里更合适；追加形容词会让同一项目的标题长度参差不齐，也不利于按版本号检索/对账。
>
> 一个版本号对应一次「可感知的变更」，不要一个版本号塞多件无关的事；也不要改完代码不 bump 版本号。

## 三、起源：家居建材 CRM（无版本号）

> 项目最早面向「家居建材定制行业（橱柜/衣柜/门窗）」，核心是「房号索引 + 分期收款 + 工序化交付」。
> 以下为 v0.9.0 之前完成的交付，Git 中无版本号。

- **第 1–8 轮完整交付**：楼盘/房号、客户、合同（明细/收款计划/增项）、收款、施工工序、照片、用户/角色/权限、审计、全文搜索（FTS5）等核心模块一次性搭成。
- **NAS 实测修复**：日志、权限、唯一约束修复；自检脚本可重复执行。
- **部署形态迁移**：NAS 部署改为 fnOS Compose 项目形态，补充界面管理入口与路径约定。
- **房号级联修复**：修复房号级联失效与房号静默误选。
- **部署坑记录**：补充 trim-cli 覆盖上传与 .dockerignore 两个部署坑。
- **单元白名单**：单元改为固定下拉（1~9 单元），服务端白名单校验。
- **客户表单增删字段**：新增手机/微信/意向产品，迁移 `0002`。

### v1.7.6（2026-10-30）

- **类型**：fix（微信域名验证失败的真正原因）
- **现象**：v1.7.5 部署后，微信申诉点「验证」仍报 **「访问文本资源失败，请调整后重试」**；但我这边 `curl https://crm.example.com/41abda4e….txt` 返回 200 且内容 40 字节完全一致。
- **根因**：`curl -I`（HEAD）拿到 **405 allow: GET**。FastAPI 的 `@app.get()` **不会**像 Starlette 的 `Route` 那样自动补 HEAD 方法（`APIRoute.__init__` 只取显式传入的 methods），所以只有 GET 被注册。**微信/腾讯云的域名验证器用 HEAD 探测文件存在性**，405 直接被判成「访问文本资源失败」。GET 正常 + HEAD 405 = 典型的「我这边测都通过、平台就是不过」。
- **修法（`main.py`）**：`@app.get(...)` → `@app.api_route(..., methods=["GET", "HEAD"])`，HEAD 与 GET 共用一个 endpoint（不另写逻辑，避免两条路径行为漂移）。
- **自检**：`tests/test_verify_file.py` 增 2 例（路由 methods 必须含 HEAD；HEAD/GET 必须指向同一 endpoint），共 14 例；全量 `pytest` **156 passed**。本地起 uvicorn 实测：`HEAD` → `200 content-length: 40` 且不发 body；`GET` → 200 内容正确；`data/verify/` 通道同样生效。
- **教训（写死）**：**凡是给「外部平台抓取」用的端点，必须 GET + HEAD 双支持并各自实测**。curl 默认发 GET，`-I` 才发 HEAD——只用 GET 自测会漏掉整类问题。以后新增 robots.txt、验证文件、健康检查这类「机器读」的端点，一律检查 HEAD。
- **回滚点**：`hvaccrm:pre-1.7.5`（= v1.7.5 镜像）。

- **修法（`app/static/app.css`，仅桌面端 `@media (min-width:781px)` 块）**：`.date-text` 显式 `white-space: normal` + `word-break: break-all`（恢复 2 行 × 2 字），并把宽度由 `2em` 放宽到 `2.1em`（给 CJK 字形亚像素舍入留约 1px 余量，避免某些字体/缩放下退化成 1 字 1 行）；`跳过原因` 的等宽公式里的 `2em` 同步改为 `2.1em`，保持「跳过原因 = 完工备注 + 施工日期 + 日期控件 + 两处 gap」的对齐关系。

### v1.9.2（2026-10-31）

- **类型**：fix（容器重建后公众号功能失效 —— Chromium profile 锁残留）
- **现象**：v1.9.1 部署后，容器内 `login_state()` 抛 `Chromium 启动超时（CDP 端口无响应）`。v1.9.0 时同样的调用是正常的。
- **根因**（chrome.log 原文）：
  ```
  The profile appears to be in use by another Chromium process (50)

  ```
  `SingletonLock -> d617285a5ae5-50` 里记着**上一个容器的 hostname**。登录态要持久化所以 profile 放在 `/data`（跨容器保留），但锁文件也跟着留下了；容器重建后 hostname 变化 → Chromium 认定 profile 被「另一台机器」占用 → 拒绝启动。

- **验证**：容器内 `rm -f Singleton*` 后 `login_state()` 立即恢复 `{'ok': True, 'logged_in': False, 'qr': True}`；195 tests passed。
- **教训**：**任何把浏览器 profile 放在持久卷的容器化方案，都必须处理 SingletonLock**——否则「第一次能用、重建后失效」这种问题会在最不可预期的时候炸。

### v1.11.0（2026-11-02）

- **类型**：feat（备份去重：全量打包 + 内容指纹相同则跳过）
- **需求**：「HVAccRM 使用频率低，可能几天才录入一次数据，但备份需要每天做——如何在保证备份的前提下，去掉重复性备份。」
- **背景数据**（线上实测）：db 主文件 532 KB、WAL 16 KB、**media 102 MB**。即备份体积的 **99.5% 是媒体**，
  而照片上传后基本不再改动 → 每天重复打包本质上是在复制同一批 102MB 文件。
- **方案取舍**（需求方拍板）：
  - 选 **「全量 + 跳过重复」**（数据没变就整个跳过），不做增量/媒体引用那套；
  - **保留份数 30 份不变**，不引入时间跨度约束，不做周期强制全量。
- **核心实现**（`app/services/backup.py`）：
  - `_db_fingerprint()`：先 `sqlite3.Connection.backup()` 拷一份副本 → **排除日志类表** → `VACUUM` 规范化 → 算 sha256。
    用规范化副本而非直接 hash 主库：WAL 模式下改一行也可能改布局，而 checkpoint/VACUUM 即使数据未变也会重写字节。
  - `_media_fingerprint()`：遍历 media，对 `(相对路径, 大小, mtime_ns)` 排序后哈希。不读文件内容，千级文件毫秒级。
  - `compute_fingerprint()` = `sha256(db_fp + ":" + media_fp)`；存 `app_settings` 的 `backup.last_fingerprint` / `backup.last_fingerprint_at`。
  - `run_backup_job(db, force=False)`：先算指纹，与上次相同 → 直接返回 `{"skipped": True}` 并记日志；否则打包，成功后写指纹。
  - 手动「立即备份」路由改为 `run_backup_job(db, force=True)`——点击是明确的「我现在就要一份」意图，不受去重影响。
- **排除哪些表（方案一，需求方选定）**：`audit_log` / `share_visits` / `sms_codes`。
  这三张跟随登录、分享访问、发码**自然增长**，若计入指纹则「业务数据没变、指纹却天天变」，跳过永不触发。
  它们**仍照常打进备份包**，只是不作为「是否值得出新包」的依据。
- **⚠️ 两个踩到的坑（已修，均补了回归测试）**：
  1. **自我指涉**：指纹本身存在 `app_settings` 里，而 `app_settings` 属于业务表 → 写指纹会改变指纹，
     导致跳过永不成立。修法：算指纹时把 `backup.last_fingerprint*` 这两个键一并排除。
     （首轮实测发现：连续三次调用全部 `skipped=False`，正是此因。）
  2. **同秒覆盖**：同一秒内连续两次手动备份，`crm-backup-<stamp>.zip` 文件名相同会互相覆盖。
     新增 `_unique_archive_path()`，冲突时追加 `-2` / `-3` 后缀。
- **后台页面**：备份管理页新增「智能跳过重复备份」说明卡（显示最近一次实际生成备份的时间、跳过语义、哪些日志不计入）；
  新增 `.card.note-card` 样式（弱底色 + 左侧细线，与既有视觉方向一致）。
- **自检**：
  - 独立脚本 7 项：VACUUM INTO 三次同哈希、只写日志表指纹不变、改业务表指纹变、媒体增删可追踪、同内容顺序无关；
  - 端到端 6 步（线上容器内实跑）：首次 `skipped=False` → 未变 `True` ×2 → 只写审计日志 `True` → 改业务数据 `False` → 之后 `True`，
    最终只产生 2 个 zip，完全符合「有变更当天必备份、无变更不重复」；
  - **285 tests passed**（新增 10 例：含自我指涉回归、三次连续跳过、force 覆盖、媒体增删）；
  - **SW 缓存 `v68→v69`**。
- **已知边界**：跳过时当天不会产生新 zip，页面「现有备份」列表的最近日期会停留在最后一次实际变更日——这是预期行为，
  说明卡里已写明「最近的一份备份仍完整可用」。
- **回滚点**：`hvaccrm:pre-1.11.0`（= v1.10.6 镜像）。

### v1.12.0（2026-11-08）

- **类型**：feat（合同结算开关 + 核算模块独立成页 + 结算后写冻结合同）
- **需求**：把「关账」这个动作显式化。原来的问题有三个：
  1. 利润核算是**全量口径**，把在制合同、还没完工的合同一起算进去，看不出「这个月真正结掉的项目赚了多少」；

- **方案要点**（与需求方对齐的口径）：
  - `Contract.settled` **与 `status` 正交**：`status` 说业务流转（active/done/void），`settled` 说财务关账（0/1）。
    不把 `settled` 塞进 status 枚举，是因为两者的生命周期不同步——合同可以是 done 但还没对完账，也可以是 active 就提前关账。
  - **结算前置硬校验**：有未完成工序（pending/doing 等非终态）时不许结算；作废合同不许结算。
    「先干完再关账」写进 `can_settle()`，不做成提示后仍可继续的软警告。
  - **冻结只留一个出口** `app/services/settlement.py`：所有写入口（收款 / 费用 / 施工 / 合同编辑）
    统一调 `block_reason()`，不在路由里各写一遍 `if contract.settled`。
    新增入口漏拦的代价是核算数字失真，而且事后极难发现，所以宁可多绕一层函数。
- **新增核算模块**（`app/routers/accounting.py` + `app/services/overview.py`）：
  - `/accounting/profit` —— 利润核算，**全量口径**（含在制合同），日常经营视角；
  - `/accounting/settlement` —— 核算，**只统计已结算合同**，关账视角；
  - `/accounting` 302 → `/accounting/profit`；
  - 两页的聚合、筛选、排序都走 `services/overview.build_ctx()`。
    拆出来的原因很具体：原来成本页一份毛利算法、核算页再抄一份，改了一个忘另一个就会出现「两个页面对不上」，
    这种 bug 查起来最费时间。

- **旧地址兼容**：`/costs/overview` → 302 `/accounting/profit`，**带原查询串**（筛选/排序状态不丢）。
  用 302 不用 301 —— 301 会被浏览器永久缓存，将来想改回来就难了。
- **冻结范围**（已结算合同的写操作）：
  | 入口 | 行为 |
  |---|---|
  | 登记收款 / 退款（新增、修改、删除） | 拦截，`登记收款` |

### v1.12.9（2026-11-08）

- **类型**：fix（列表页表格字号不一致）
- **现象**（用户报）：「客户」和「楼盘 / 房号」两页对比，楼盘页表格里的字明显偏大。
- **根因**：`app.css` 里并存两套表格密度——
  `th, td { padding: .45rem .5rem }` + td 继承 body 的 **15px**，
  和 `table.tight th, table.tight td { padding: .35rem .45rem; font-size: .88rem }`（**13.2px**）。
  而 `th` 两边都固定 `.8rem`（12px），所以**漏写 `tight` 的页面会变成「表头比内容还小」**，
  视觉上就是「这一页的字偏大」。全仓库裸 `<table>` 共 6 处，都是历史遗漏：
  `projects/list`（楼盘 / 房号）、`contracts/list`（合同台账）、`payments/list`（收款流水）、
  `payments/overdue`（欠款预警，页内两张表还一大一小）、`admin/users`、`admin/stages`。
- **修法**：这 6 处一律补 `class="tight"`（把 `tight` 当列表页默认，`kv` / `tasks` / `js-stack` 保留例外）。
  **没动 CSS**：全局改默认字号会波及详情页里的 key-value 表，风险比补 6 个 class 大得多。
- **自检**：新增 `tests/test_table_density.py`（2 例）——
  扫描 11 个列表模板，任何裸 `<table>` 直接报出行号；另一例把 `.88rem` / `15px` 两个数字钉住，
  防止哪天顺手改了 CSS 口径。反证过：把 `projects/list` 改回裸 `<table>`，测试确实失败。
  全量 **346 tests passed**。

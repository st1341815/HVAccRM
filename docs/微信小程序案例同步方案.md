## 一、结论先行

| 问题 | 结论 |
|---|---|
| 能不能做 | **能，而且比想象中便宜**——但**不能**让小程序直连你家的 NAS |
| 硬门槛 | 微信小程序的「服务器域名」**只允许 HTTPS 默认端口 443**，且**必须 ICP 备案域名**；家庭宽带**外网 443 被运营商封**（实测 `https://crm.2ii.cn/health` = 000，`:8443` = 200），这条路物理上走不通 |
| 破局点 | **翻转数据流向**：不是小程序来拉 NAS，而是 **NAS 主动往云端推**。NAS 只做出站 HTTPS 请求 → 不需要公网入站、不需要备案、不需要 443、不需要暴露 NAS |
| 推荐架构 | **NAS 推 → 微信云开发（CloudBase）存副本 → 小程序读云开发 → `onShareAppMessage` 出原生分享卡片** |
| 成本 | 约 **19.9 元/月**（云开发基础套餐）= **239 元/年**。0 服务器、0 域名、0 备案 |
| 数据主权 | 只推**已脱敏的公开案例字段**。客户姓名/电话/合同额/完整房号**永不出 NAS** |
| 额外收益 | 客户看图走腾讯 CDN，**NAS 关机/断网/重启不影响客户打开分享卡片** |
| 工作量 | 后端 3~4 天 + 小程序 3~5 天 + 联调 1~2 天 ≈ **1.5~2 周**（单人） |

**一句话架构**：NAS 是唯一真源，云开发是"只读的对外展示副本"，小程序是"能生成微信原生分享卡片的图册"。

## 二、为什么"小程序直连 NAS"不可行

### 2.1 规则对照表

| 约束 | 官方规则 | 你的现状 |
|---|---|---|
| 协议 | `wx.request` 只允许 **https** | ✅ 已有 `crm.2ii.cn:8443` |
| 端口 | **域名不允许配置端口**（默认 443） | ❌ 你只有 8443 |
| 443 可用性 | —— | ❌ **实测 000（家宽封 443）** |
| 域名 | 必须 **ICP 备案** | ⚠️ 解析到家庭宽带 IP，备案基本过不了（家宽无接入资质） |
| IP | 不支持 IP 直连（开发调试仅局域网放宽） | ❌ `192.168.11.8` |
| web-view | 需**企业主体** + 业务域名（同样 443 + 备案） | ❌ |

### 2.2 结论

**任何"小程序 ← 反向访问 NAS"的方案，都要先解决「443 + 备案 + 家庭宽带资质」三连**，这三项都不在我们能控制的范围内。
→ 本方案**完全不碰这条路**。

## 三、总体架构

```
┌─────────────────── 飞牛 NAS (192.168.11.8) ───────────────────┐
│  HVAccRM 容器                                                  │
│                                                                │
│  finish_task()   ← 施工工序完工（现有逻辑，不动）              │
│      ↓                                                         │
│  create_case_for_task()  → cases / case_images (SQLite)        │
│      ↓  新增：写一行「推送任务」                               │
│  wx_push_jobs (status=pending)                                 │
│      ↓                                                        │
│  APScheduler 每 30 秒扫一轮 → services/wechat_push.py           │
│      ① 生成分享版图片（1440px / JPEG q82 / **剥 EXIF**）        │
│      ② tcb/uploadfile → 云存储 fileID                          │
│      ③ tcb/databaseupdate|add → 云数据库文档                   │
│      ④ 回写 cases.wx_sync_state / wx_images / wx_synced_at     │
└───────────────────────┬────────────────────────────────────────┘
                        │  只出站 HTTPS（api.weixin.qq.com）
                        │  无需公网入站 / 无需备案 / 无需 443
                        ▼
┌──────────────── 微信云开发 CloudBase ─────────────────────────┐
│  云数据库  cases      （只读副本，已脱敏，_id = share_token）   │
│  云数据库  members    （内部成员 openid 白名单）               │
│  云存储    cases/<token>/0.jpg … n.jpg（CDN 直出）             │
│  云函数    whoami / listCases（内部列表鉴权）                  │
└───────────────────────┬────────────────────────────────────────┘
                        │  wx.cloud（不走"服务器域名"白名单）
                        ▼
┌──────────────────── 微信小程序 ──────────────────────────────┐
│  案例库(列表)  →  案例详情(图集)  →  onShareAppMessage        │
│                                          ↓                    │
│                              微信好友聊天：小程序卡片         │
│                                          ↓                    │
│                              客户点开 → 详情页（免登录）       │
└───────────────────────────────────────────────────────────────┘
```

### 三个关键设计判断

1. **单向、异步、可重试**。`finish_task` 里**不做**网络请求（上传 6 张图要 2~10 秒，会卡住完工按钮）。只写一行 outbox，后台慢慢推。
2. **云开发是"投影"不是"数据库"**。所有写入永远只从 NAS 发起；小程序端**只读**。这样永远不会出现"两边不一致该信谁"的问题。
3. **分享令牌即主键**。云文档 `_id` 直接用现有的 `Case.share_token`（`secrets.token_urlsafe(16)`），天然不可枚举、天然幂等 upsert、天然和现有 H5 分享链路共用一套失效逻辑。

## 四、数据契约（推什么、不推什么）

### 4.1 云数据库集合 `cases`（一篇文档 = 一个案例）

```json
{
  "_id": "Hk3nQ8vT2pLx9aBcDeFg",         // = Case.share_token（主键，不可枚举）
  "site": "颐园清苑 6#",                  // 楼盘 + 楼栋 ← 注意：不含单元/房号
  "project": "颐园清苑",
  "stage": "前期施工",
  "work_date": "2026-10-20",
  "product_type": "地暖",
  "installer": "张师傅",                  // 可配置是否显示，默认显示
  "cover": "cloud://prod-xxx.xxxx/cases/Hk3n…/0.jpg",
  "images": [
    { "f": "cloud://…/cases/Hk3n…/0.jpg", "w": 1440, "h": 1080 }
  ],
  "expires_at": "2026-11-24 00:00:00",   // 空 = 不限
  "disabled": false,                      // 手动失效开关
  "sync_ver": 3,                          // 本地每次变更 +1，用于对账
  "published_at": "2026-10-25T22:10:00+08:00"
}
```

### 4.2 字段映射与隐私红线

| 本地字段 | 推送？ | 说明 |
|---|---|---|
| `Case.site_label`（楼盘 + 楼栋） | ✅ | 对外唯一的位置信息 |
| `Case.room_label`（楼盘+楼栋-单元-房号） | ❌ **绝不** | 完整房号在云端**零痕迹** |
| `Case.stage` / `work_date` / `product_type` | ✅ | 展示主体 |
| `Case.installer_name` | ⚠️ 可配 | 建议保留姓氏（"张师傅"），必要时脱敏成"施工师傅" |
| `Case.share_token` | ✅ | 作为 `_id` |
| `Case.share_expires_at` / `share_disabled` | ✅ | 见 §6.3 失效语义 |
| `Case.share_max_views` / `share_views` | ❌ | 客户端计数不可信，次数限制只保留在 H5 分享页 |
| `Customer.*`（姓名/手机/微信） | ❌ **绝不** | |
| `Contract.*`（金额/收款/优惠） | ❌ **绝不** | |
| 图片原图 EXIF（**含 GPS 坐标**） | ❌ **必须剥离** | 见 §6.2 |

> **红线一句话**：云上只存在"一个陌生人也该看得见的数据"。这条守住，方案就没有后患。

### 4.3 云存储路径规范

```
cases/<share_token>/0.jpg   ← 封面（另出一份 800×640，5:4，供分享卡片）
cases/<share_token>/1.jpg
cases/<share_token>/2.jpg
…
```
- 路径用 token 而非自增 id → 无法遍历。
- 覆盖上传同名路径 = 天然幂等（重推不产生垃圾文件）。
- 顺序变化（用户调 `sort_order` / 删中间图）→ **整体重传 + 覆写**，旧的多余文件随后清理（见 §6.4）。

## 五、后端改造（HVAccRM 侧）

### 5.1 新增表 `wx_push_jobs`（迁移 `0016_wx_push`）

```python
class WxPushJob(Base):
    __tablename__ = "wx_push_jobs"

    id = Column(Integer, primary_key=True)
    case_id = Column(Integer, ForeignKey("cases.id", ondelete="CASCADE"), nullable=False)
    action = Column(String, nullable=False, default="upsert")   # upsert | delete
    status = Column(String, nullable=False, default="pending")  # pending|running|ok|failed
    attempts = Column(Integer, default=0)
    next_retry_at = Column(String)      # 指数退避：1m / 5m / 30m / 2h / 12h
    last_error = Column(String)
    created_at = Column(String, nullable=False, default=now_iso)
    updated_at = Column(String)
```

唯一性：`(case_id)` 上建**部分唯一索引**（`WHERE status IN ('pending','running')`），保证同一案例队列里只有一条在途任务——重复完工 / 重复点"重新同步"不会堆任务。

### 5.2 `cases` 表加 5 列

```python
wx_sync_state = Column(String, default="none")   # none|pending|ok|failed
wx_sync_ver   = Column(Integer, default=0)       # 本地变更版本号
wx_synced_at  = Column(String)
wx_images     = Column(String)                   # JSON：远端 fileID 列表（对账/清理用）
wx_last_error = Column(String)
```

### 5.3 触发点（全部"写队列即返回"）

| 位置 | 动作 |
|---|---|
| `services/cases.create_case_for_task()` 末尾 | `mark_dirty(case, "upsert")` |
| `routers/cases` 的 `upload_images` / `delete_image` / `sync_photos` / `set_share_settings` / `disable` / `enable` | `mark_dirty(case, "upsert")` |
| `services/cases.delete_case()` | `mark_dirty(token, "delete")`（删前先取 token） |

`mark_dirty()` 只做两件事：`case.wx_sync_ver += 1`、UPSERT 一条 job。**零网络 IO。**

### 5.4 推送 worker（`services/wechat_push.py`）

```python
def run_once(db, limit=5) -> dict:
    for job in claim_jobs(db, limit):          # pending 且 next_retry_at <= now
        try:
            if job.action == "delete":
                remote_delete(case_token)
            else:
                push_case(db, case)
            job.status = "ok"
        except WeChatError as exc:
            job.attempts += 1
            if job.attempts >= 5:
                job.status = "failed"
                case.wx_sync_state = "failed"
            else:
                job.next_retry_at = backoff(job.attempts)
```

调度：`scheduler.py` 里加 `sched.add_job(push_job, "interval", seconds=30, id="wx_push")`，与现有 backup job 同一模式（`reload_*` 已在用，骨架现成）。

### 5.5 微信 API 客户端要点（都是坑）

| 项 | 做法 | 为什么 |
|---|---|---|
| `access_token` | 用 `POST /cgi-bin/stable_token`（**不要** `/cgi-bin/token`） | `token` 接口每次调用都会踢掉上一个；`stable_token` 不会互相失效，重试/并发安全 |
| token 缓存 | 存内存 + 落 `app_settings`（`wx.token` / `wx.token_exp`），提前 5 分钟续期 | 容器重启不必重新取 |
| 图片上传 | 两步：`tcb/uploadfile` 拿 `{url, token, authorization, file_id, cos_file_id}` → `POST url`（form: `key=path, Signature=authorization, x-cos-security-token=token, x-cos-meta-fileid=cos_file_id, file=@…`） | 官方唯一路径 |
| 文档写入 | 先 `tcb/databaseupdate`（`db.collection("cases").doc("<id>").set({data:{...}})`）；`updated=0` 时走 `tcb/databaseadd` | HTTP API 没有真正的 upsert，`set` 语义需自行兜底 |
| 删除 | `tcb/databasedelete` + `tcb/batchdeletefile` | 只删文档会留下孤儿图片，长期烧存储费 |
| HTTP 库 | `httpx`（现有 requirements 里没有，需加） | 支持超时/重试/连接池 |
| 密钥 | `WX_APPID` / `WX_SECRET` / `WX_ENV` 走容器 env（`config/deploy.env`），**绝不入库、绝不进 git** | AppSecret 泄露 = 小程序后台被完全接管 |

### 5.6 后台新增页面「小程序同步」（`/admin/wx-push`）

- 顶部状态条：`已同步 N / 待推 M / 失败 K`（失败红色）
- 表格：案例 / 状态 / 版本 / 最后同步时间 / 最后错误 / 操作（重推、删除远端）
- 「批量回推历史案例」按钮（首次上线时把存量案例一次性推上去，走同一队列逐条推）
- 「测试连通性」按钮（取 token + 查一次数据库，验证配置）
- 权限：仅 `admin:setting`

## 六、同步引擎的四个硬细节

### 6.1 幂等
- 文档 `_id = share_token` → 重推覆盖同一篇，不产生重复案例。
- 图片路径固定 → 覆写同名文件。
- `wx_sync_ver` 单调递增，云端 `sync_ver` 小于本地才覆盖（防乱序覆盖新数据）。

### 6.2 图片转码（别把原图直接推上去）

```
原图（1920px JPEG ~1.5MB）
  → 分享版：长边 1440 / JPEG q82 / **strip EXIF·ICC** ≈ 250~350KB
  → 封面版：800×640（5:4 裁切）/ JPEG q85 ≈ 120KB
  → 本地缓存到 media/cases/<id>/wx/<idx>.jpg（源图 hash 变了才重造）
```

- **必须 strip EXIF**：手机拍照带 GPS，原样推到云上等于公开工地的精确坐标。本方案里最容易被忽略的隐私漏洞。
- 6 张图 ≈ 1.8MB → 4G 下 3~5 秒打开，可接受。

### 6.3 失效语义（两套口径要分清）

| 限制 | H5 分享页（现有） | 小程序 |
|---|---|---|
| 手动失效 `share_disabled` | ✅ 生效 | ✅ 推送 `disabled:true`，详情页显示"已失效" |
| 时间到期 `share_expires_at` | ✅ 生效 | ✅ 推送 `expires_at`，客户端比对本地时间（可被改机绕过，可接受） |
| 次数上限 `share_max_views` | ✅ 生效 | ❌ **放弃**（客户端计数不可信，做完等于自欺） |

> 产品规则：**「要限次数就发 H5 链接，要好看就发小程序卡片」**——两种分享方式并存，各管一段。

### 6.4 清理（防止云上越积越多）
- 案例删除 → `databasedelete` + `batchdeletefile(旧 fileID 列表)`
- 图片从 6 变 4 → 重传 4 张，然后 `batchdeletefile` 掉多出来的 2 个 fileID（依据本地 `wx_images` 旧值）
- 每日 05:00 对账（P2 可选）：列出云端 `cases/*` 前缀下的文件，不在任何 `wx_images` 里的 → 记日志，人工确认后清理

## 七、小程序设计

### 7.1 页面结构（4 个页面足够）

```
pages/
  index/    案例库        tabBar ①  —— 列表、筛选（工序/产品类型/日期）、下拉刷新、触底加载
  case/     案例详情      —— 图片轮播 + 九宫格、meta 信息、底部「分享给客户」按钮
  about/    关于我们      tabBar ②  —— 企业介绍、服务范围、联系方式（**审核必需**，见 §8.9）
  mine/     我的（可选）  —— 绑定状态、退出、跳 H5 后台
```

**详情页是唯一有"对外"职责的页面**，设计要点：
1. 首屏就是图（客户只看图），meta 信息放在图下方的小卡片
2. 图片点击 → `wx.previewImage` 全屏可缩放左右滑
3. 顶部品牌条（商号 + Logo），底部一句"仅作展示参考"
4. 右上角 `…` → 转发（微信原生）

### 7.2 分享卡片（本方案的核心价值）

```js
// pages/case/index.js
onShareAppMessage() {
  const c = this.data.case
  return {
    title: `${c.product_type || ''}施工案例 · ${c.site}`,   // 例：地暖施工案例 · 颐园清苑 6#
    imageUrl: c.cover,        // 支持云文件ID，5:4 封面已单独生成
    path: `/pages/case/index?id=${c._id}`,                 // 客户点开直达详情
  }
}

onShareTimeline() {           // 可选：分享到朋友圈（单页模式，只读展示 OK）
  return { title: `${...}`, query: `id=${this.data.case._id}`, imageUrl: this.data.case.cover }
}
```

**卡片形态**（客户在聊天里看到的）：

```
┌─────────────────────────────────┐
│  ┌───────────────────────────┐  │
│  │   （5:4 施工实景封面图）   │  │
│  └───────────────────────────┘  │
│  地暖施工案例 · 颐园清苑 6#      │
│  ▣ 小程序                       │
└─────────────────────────────────┘
```

点开即进小程序详情页，**不需要关注公众号、不需要登录、不需要复制链接**——这就是比现在发 `https://crm.2ii.cn:8443/cases/share/xxx` 强的地方。

### 7.3 认证：三级可见性

| 层级 | 谁能看 | 实现 |
|---|---|---|
| **详情页**（分享落地） | 任何人（凭 token） | 客户端 `db.collection('cases').doc(id).get()`；安全规则：所有人可读、仅服务端可写 |
| **列表页** | 仅内部成员 | 云函数 `listCases`（校验 `members` 集合里的 openid）→ 返回分页结果 |
| 写入 | 只有 NAS | 客户端无写权限（安全规则 `write: false`） |

内部成员绑定流程（3 步，不做账号体系）：
1. 小程序端首次进入 → 云函数 `whoami` 返回 `openid`
2. 页面显示一串短码 + 「复制」
3. 管理员在 HVAccRM 后台「小程序成员」粘贴 openid → 写入云端 `members` 集合

> 内部使用者就 1~3 人，**不值得**做微信登录 → 账号绑定的完整链路。

### 7.4 为什么列表页要做鉴权

案例库全量公开 = 竞争对手能统计你一年做了多少单、在哪些楼盘、什么产品结构。这是商业情报，不是营销素材。
**详情页公开（分享必需），列表页收口（内部用）** —— 分层是免费的。

### 7.5 "仅特定用户可见"是怎么实现的

1. **详情页凭 `share_token` 打开** —— 16 字节随机串，不可枚举，等于"只有拿到链接的人能看"
2. **列表页走云函数 + openid 白名单** —— 外人即使打开也翻不到全部案例
3. **后台关闭"允许被搜索"** —— 搜名字搜不到，只能通过你发的卡片进来

三条合起来 = "客户只有在收到我的卡片时才能看"，比任何"密码验证"都干净。

## 十、风险与坑

按杀伤力排序：

1. **⚠️ 云开发免费环境上线后 15 天到期**。微信 2025 年起"免费环境"只在小程序**未发布**阶段有效，**发布后第 15 天到期**，不转付费直接停服销毁。→ 提审前就把付费环境准备好。
2. **⚠️ AppSecret 泄露 = 小程序被接管**。只走 NAS 容器 env；若在微信后台点过"重置密钥"，必须同步改 `deploy.env` 并重启容器，否则推送全挂。
3. **⚠️ 审核"内容过少"被拒**。只有"列表+详情+分享"的小程序常被判"功能过于简单"。→ 必须补「关于我们/服务介绍/联系方式」页。
4. **⚠️ 主体与类目**。个人主体不能用于本场景（类目与名称双重受限）；个体户必须走「企业」类型。类目若提示"需微信认证"，先退回「工具」类试。
5. **⚠️ EXIF GPS**（见 §6.2）——技术债，但属隐私事故级别，必须做在 P1。
6. **CDN 流量按量计费**。图片不压缩会把 5GB 烧穿（一次浏览变 15MB）。转码参数不能省。
7. **`access_token` 互踢**。用 `stable_token`；不要自己写"缓存 2 小时"然后多进程各取各的。
8. **孤儿文件**。删除/改图只删文档不删文件 → 云存储慢慢涨。`wx_images` 存旧 fileID 就是为了清理用。
9. **令牌变更**。若未来做"重新生成分享令牌"，旧卡片会失效且云端留旧文档 → 变更时同步 `delete` 旧 `_id`。
10. **审核员会真的点你的页面**。提审说明里给的 token 必须**真实、未过期、图片能加载**。用专门造的演示案例，别用真实客户的。

### 11.1 如果现在就想改善分享效果（0 成本，今天可做）

在决定上小程序之前，两个"半小时见效"的动作：

1. **给现有分享页加社交 meta**：`<meta property="og:title">` + `og:image`（用第一张缩略图）。微信在聊天里抓取纯链接时会读 `<title>` 和首图，卡片会从"一行灰字"变成"标题 + 缩略图"。
2. **加"生成二维码"按钮**：把 `https://crm.2ii.cn:8443/cases/share/<token>` 转成二维码图片（纯前端库即可，无需后端）。发二维码比发带端口的链接体面，而且能让客户把案例"留在相册里"。

> 这两步不替代小程序，但能在 1.5 周开发期内先把"分享给客户"做得像样，避免为了等小程序而卡住业务。

**推荐节奏：**

```
第一步（今天，0 元）：H5 分享页加 og 卡片 + 生成二维码 → 立刻能漂亮地发给客户
第二步（1~2 周）：边发边把小程序做出来（个体户主体、工具类目）
第三步（发布后）：小程序卡片成为主路径，H5 作为"限次数分享"的补充
```

## 附录 C：故障排查速查

| 现象 | 优先查 | 定位方法 |
|---|---|---|
| 完工后云端没数据 | 队列是否入队 | 查 `wx_push_jobs` 有无 pending 行 |
| 一直 pending 不动 | 调度是否注册 | 看容器日志有无 `wx_push` job 启动记录 |
| 报 40001 / 42001 | access_token 失效 | 走 `stable_token` 重取；检查是否有别处在用 `token` 接口 |
| 图片上传失败 | `cos_file_id` / `authorization` 是否按字段名传 | 对照 §5.5 表单字段名逐个核 |
| 小程序打开白屏 | 云环境是否到期 | 后台看云开发环境状态（免费环境发布后 15 天） |
| 小程序读不到文档 | 数据库权限规则 | 安全规则应为「所有人可读、仅服务端可写」 |
| 客户打开显示"已失效" | `expires_at` / `disabled` | 后台外链管理页看状态 |
| 图片能传但显示不出来 | fileID 是否含环境前缀 | `cloud://<env>.<bucket>/<path>` 格式核对 |

## 附：为什么这套方案也"AI 编程友好"

- **改动面收敛**：后端只碰 1 张新表 + 1 个新 service + 1 个新路由，现有业务逻辑一行不用改（`finish_task` 只加一个 `mark_dirty`）。
- **可验证性强**：每个阶段都有机器可判定的验收（token 能取到 / 云端出现文档 / 手机能看图），不依赖"感觉对不对"。
- **失败可隔离**：推送失败不影响本地业务（完工照常、案例照常生成），只是后台多一条失败记录——这正是"把外部依赖放到队列后面"的价值。
- **回滚成本低**：关掉 `wx_push_enabled` 即回到原行为，云端数据可整体清空。

[Heading1] 家居建材客户管理系统（CRM）开发规格说明书
[Heading2] 一、项目概述
[Heading3] 1.1 基本信息
[Compact] 项目名称：家居建材客户管理系统（CRM）
[Compact] 运行环境：用户自有 NAS 平台（x86 架构，Debian 操作系统）
[Compact] 用户规模：个人使用起步，未来扩展至 20 人以内
[Heading3] 1.2 使用场景
[FirstParagraph] 面向家居建材行业（定制类，如橱柜、衣柜、门窗等），专注于已成交客户的全生命周期管理。覆盖从合同签订、收款、施工安装到完工留档照片的全流程。
[Heading3] 1.3 核心定位
[FirstParagraph] 本系统并非通用 CRM，而是针对家居建材行业的垂直管理工具，具备以下三大核心特征： 1. 房号为核心索引：采用“楼盘-房号”结构组织数据。 2. 款项分期管理：严格区分“应收计划”与“实际收款”。 3. 工序化交付：内置标准施工流程（量尺 → 复尺 → 下单 → 到货 → 安装 → 验收 → 回访）。

[Heading2] 六、核心业务规则
[Heading3] 6.1 房号录入流程
[Compact] 级联选择：先选楼盘 → 再选楼栋 → 最后输入房号。
[Compact] 快捷创建：支持在录入现场直接新建楼盘或房号。
[Compact] 模糊搜索：同一楼盘下，输入“1203”应列出所有楼栋的 1203 房号。
[Heading3] 6.2 收款管理规则
[Compact] 三数核对：合同总额 ≠ 已收 ≠ 应收，系统需实时计算差值。
[Compact] 逾期重算：定时任务每日扫描 payment_plans，若 due_date < 今日 且未付清，状态更新为 overdue。
[Compact] 增项处理：增项必须走 change_orders，并同步追加 payment_plans。
[Compact] 超额拦截：入库前校验 sum(payments) + 本次金额 ≤ total_amount + 增项总额。
[Compact] 视图计算：前端展示应收合计、已收合计、未收金额及回款率（已收/应收）。
[Heading3] 6.3 施工任务规则
[Compact] 自动建单：客户建单时按模板自动生成 9 个标准节点任务。
[Compact] 前置依赖：按 sort_order 控制，上一节点未完成，下一节点仅显示 ready，禁止开工。
[Compact] 跳过机制：跳过节点必须填写原因。
[Compact] 延期预警：若 planned_end < 今日 且 status != done，自动标记延期，首页红字提示。
[Heading3] 6.4 照片管理规范
[Compact] 存储路径：data/media/{customer_id}/{kind}/{uuid}.jpg，数据库仅存相对路径。
[Compact] 命名规则：严禁使用客户名或房号作为文件名/目录名。
[Compact] 图片处理：保留原图 + 生成 WebP 缩略图（长边 1280px，质量 80）。
[Compact] 上传接口：POST /api/customers/{id}/photos (multipart)，支持多张上传。
[Compact] 元数据：服务端读取 EXIF DateTimeOriginal 和 GPS（可选）。
[Compact] 去重：按文件 Hash 判重，重复文件仅存储一份物理文件。
[Compact] 安装工限制：仅允许 POST photos 及查看自己负责的客户，无删除权。

[Heading2] 十、NAS 特有注意事项
[Compact] 权限模型：容器内禁止 root 运行，固定 UID/GID（如 1000），通过环境变量映射。
[Compact] 路径分离：配置、数据、缓存、日志四个目录物理分离，全部通过卷挂载。
[Compact] 远程挂载：若数据在 NFS/SMB 挂载点，需特别注意文件锁和 inode 行为。
[Compact] 磁盘休眠：日志级别设为 INFO 以上，避免频繁写日志或轮询扫描阻止硬盘休眠。
[Compact] 多架构构建：使用 docker buildx 一次构建 linux/amd64 和 linux/arm64。
[Compact] 内存限制：compose 中必须配置 mem_limit。
[Compact] HTTPS 策略：容器仅监听 HTTP，HTTPS 由 NAS 反代（Let’s Encrypt）处理。
[Compact] 备份策略：每天凌晨执行 VACUUM INTO 或 .backup 至 data/backups/，保留最近 30 份。
[Compact] 并发写处理：SQLite 20人并发写会有短暂锁等待，写操作需封装重试机制（database is locked 时退避重试 3 次）。
[Compact] 首次启动：自动建库建表 + 创建 admin，通过环境变量 ADMIN_USER / ADMIN_PASS 传入一次。

[Heading2] 十一、开发协作规则
[Compact] 单轮单模块：每轮只做一个模块，跑通并经用户确认后方可继续。
[Compact] 交付完整性：每次交付必须包含：文件清单 + 完整代码 + 运行命令 + 验证方法。
[Compact] 报错规范：报错信息必须贴全文，禁止概括。
[Compact] 数据安全：动数据前必须先备份。
[Compact] 版本控制：每次交付后执行 git commit。
[Compact] 诚实原则：遇到不懂的代码直接询问，禁止假装懂或猜测。
[Compact] 需求变更：需求变动随时提出，“简化版”指令可砍掉花哨功能。

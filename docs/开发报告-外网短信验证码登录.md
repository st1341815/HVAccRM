# 开发报告：外网短信验证码登录（内外网自动识别）

- 项目：HVAccRM（暖通空调客户管理系统）
- 基线版本：v1.7.7（线上 healthy，2026-10-31 实测）
- 报告日期：2026-10-31
- 状态：**待评审**——文末有 5 个决策点需要拍板后开工

---

## 1. 需求

登录界面增加**短信验证码登录**，且该验证仅在检测到**外网访问**（外网域名或公网 IP）时启用；**内网环境登录体验保持现状**（账号 + 密码，不加任何步骤）。

一句话概括：**外网 = 密码 + 短信双因素；内网 = 现状，零变化。**

## 2. 现状分析（全部为代码/实测事实）

### 2.1 现有认证体系

| 能力 | 现状 | 位置 |
|---|---|---|
| 登录方式 | 用户名 + 密码（PBKDF2），可选 TOTP（voluntarily 开启） | `app/auth.py` `login_submit()` |

| 会话 | 签名 cookie，12h，session_version 变更即失效 | `security.py` + `config.py` |
| 用户表字段 | **没有 mobile 字段**，只有 username / full_name / totp_* | `models.py::User` |
| 运行形态 | uvicorn `--workers 1` 单进程 | `scripts/entrypoint.sh` |
| HTTP 客户端依赖 | 无（requirements 无 requests/httpx，短信 API 需 urllib 自写或加依赖） | `requirements.txt` |
| 后台配置 | `app_settings` k-v 表 + `services/settings.py`（已有备份设置先例） | 迁移 0015 |

### 2.2 网络拓扑现状（2026-10-31 实测，与旧记忆有出入）

| 项 | 实测结果 |
|---|---|
| 容器 | `hvaccrm` 在本机（octop 宿主 = CRM 宿主），`0.0.0.0:8090→8000`，v1.7.7 healthy |
| 外网域名 `old.example.com:8443` | **已不再指向 HVAccRM**——实测返回 `iKuai OS V4` 路由器管理页（`x-arch: arm`） |
| Lucky | **进程未运行**，本机无 8443 监听 |
| Tailscale | 本机无 tailscale CLI、无 100.x 路由 |
| 外网登录历史 | `audit_log` 有真实外网记录：`1.1.1.1`（安徽移动公网，10-14）、`9.9.9.9`（Cloudflare 段，10-18）→ **证明当时的反代链路 X-Forwarded-For 透传正常**，应用能拿到真实客户端 IP |
| 本机 DNS | `old.example.com` 被解析为 `198.18.0.132`（fake-ip，网关代理分流所致），`--resolve` 直连公网 IP 才是真实结果 |

**关键结论：**

1. 外网通道正处于「断开/变更中」状态（Lucky 停了、8443 现在是爱快路由器自己的页面）。**内外网判定绝不能绑定具体入口产品**（Lucky/爱快映射/DDNSTO/CF Tunnel），必须基于请求本身的特征做通用判定——无论以后用什么方式接入，功能都自然生效。
2. 审计历史证明 XFF 链路可以透传真实 IP，这是判定的核心信号之一。
3. 真机外网联调前，需要先把外网通道恢复（爱快重新做 8443 映射 / 重启 Lucky / 或新方案）——这是部署项之一，不是本功能的开发项。

## 3. 方案设计

### 3.1 内外网判定：双信号模型（`app/net.py` 新模块）

到达 FastAPI 的请求，只有两组可信信号：

| 信号 | 内网取值 | 外网取值 | 说明 |
|---|---|---|---|
| **A. Host 头**（剥端口、小写归一） | 私网 IP（192.168.1.8 等） | 公网 IP，或命中配置的外网域名列表（`old.example.com` 等，支持 `*.example.com` 通配） | 用户心智模型里的「用什么地址访问」 |
| **B. 真实客户端 IP**（升级版 `get_client_ip`：仅当直连来源 ∈ 可信代理名单时才采信 XFF） | RFC1918 / 127.0.0.1 / 100.64.0.0/10（Tailscale，决策点 D2） | 公网 IP | 实际网络位置 |

**判定规则（fail-safe，安全优先）：**

```
is_external = 信号A=外网 OR 信号B=外网 OR (无法判定)
```

- 任一信号指向公网 → 外网（宁可多发一条短信，不可漏放一次外网登录）。
- 两个信号都明确内网 → 内网。
- 信号冲突（如内网用户经反代访问，Host=外网域名但 XFF=192.168.1.x）→ 按外网处理，但**内网用户经内网入口访问时两个信号都会是内网**，不会误伤。

**为什么不用其他方案：**

- ❌ 「全站永远开短信」：违背需求（内网免），且每天登录烧钱。
- ❌ 「在 Lucky/反代层打标记头」：与入口产品耦合，Lucky 一停全失效（本次实测已证明这个风险是真的）。
- ❌ 只看 XFF：现在 `get_client_ip()` 无条件信任 XFF 首段——若 8090 未来被直接映射到公网，攻击者可伪造 `X-Forwarded-For: 192.168.1.1` 冒充内网绕过验证。**本次顺带把这个安全弱点修掉**：加 `TRUSTED_PROXIES` 白名单（默认 `127.0.0.1,::1,172.16.0.0/12`，env 可配），名单外的直连请求其 XFF 不参与判定（其 `request.client.host` 是公网 IP → 自然判外网，fail-safe 闭环）。

**判定时机：GET /login 渲染时判一次（决定 UI 展示），POST /login 提交时再判一次（真正的执行点）**——不信任页面渲染时的状态，防止「内网开页、切外网提交」的边界，也防直接构造表单提交。

### 3.2 登录流程（外网）

```
① GET /login（判定=外网）
   └─ 渲染：账号 + 密码 + 短信验证码输入框 + [获取验证码] 按钮 + 提示「外网访问需短信验证」

② 点击 [获取验证码]（formaction 指向 /login/sms/send，账号密码随表单带上）
   ├─ 内网请求 ────────────→ 303 回登录页（提示：内网无需验证码）
   ├─ CSRF 失败 ──────────→ 400 页面过期
   ├─ 登录锁定中 ─────────→ 429 请等待 N 秒
   ├─ 账号不存在/停用/密码错 → 401「账号或密码错误」+ 计入现有失败锁定（不泄露用户名存在性）
   ├─ 账号未绑手机号 ─────→ 提示「该账号未绑定手机号，请联系管理员」（须先过密码，泄露面可接受）
   ├─ 60s 冷却 / 日限流 ──→ 提示稍后再试
   └─ 通过 ───────────────→ 生成 6 位码 → HMAC 哈希入库（TTL 5 分钟）
                             → 调短信服务商发送 → audit(sms_send)
                             → 303 回登录页，提示「验证码已发送至 139****5678」

③ 提交登录（POST /login，重新判定外网）
   密码校验 → 短信验证码校验（一次性、5 分钟内、错 3 次作废、错误计入失败锁定）→ 发会话 cookie → audit(login, auth_mode=sms)
```

**内网路径**：GET /login 判定内网 → 不渲染短信步骤；POST /login 判定内网 → 不校验 `sms_code`。**现有体验与代码行为完全不变。**

**设计要点：**

- **先验密码、后发短信**（而不是「输账号就发码」）：密码即第一道门，天然防短信轰炸（不向通过不了密码的人发短信）、防用户名枚举、省成本。
- **验证码与 user_id 绑定**：A 账号的码不能登 B 账号；两个账号绑同一手机号也不串。
- **验证码只存 HMAC-SHA256 哈希**（密钥用 `APP_SECRET_KEY` + 每条随机盐），不存明文——库文件/备份 zip 泄露也拿不到码。
- **与 TOTP 的关系**（决策点 D3）：推荐「开了 TOTP 的账号，TOTP 可替代短信」——同属第二因素（你拥有的东西），双验纯粹是负担还烧钱。默认实现为替代模式，代码上留一个开关。

### 3.5 短信服务商选型（决策点 D1）

| 方案 | 门槛 | 成本 | 集成工作量 | 建议 |
|---|---|---|---|---|
| **榛子云** | 个人注册即可、无需企业认证，充值即用，按条计费 | ~0.05 元/条 | HTTP + MD5 签名，urllib 约 30 行 | **个人自用首选** |
| 腾讯云短信 | 个人实名可申请，签名/模板报备审核 1–2 天 | ~0.045 元/条 | TC3-HMAC 签名，urllib 约 60 行 | 稳定，审核材料比阿里云松 |
| 阿里云短信 | 同上，个人签名审核最严（需与备案/应用名一致） | ~0.045 元/条 | V3 签名稍复杂 | 备选 |
| `console` provider | 无 | 0 | 验证码打进容器日志 | **开发联调必经阶段** |

推荐节奏：先用 `console` provider 完成开发与全流程自测并上线观察判定准确性 → 服务商账号下来后切换 `SMS_PROVIDER` + 填密钥 + 后台点「发送测试短信」→ 完整启用。**签名报备要提前 1–2 天去办**，不阻塞开发。

### 3.6 兜底与逃生通道（防「把自己锁外面」）

1. **后台总开关**（`sms.enabled`）：任何异常一键关掉整个功能，回到现状。
2. **内网永远免验证**：手机丢失/换号/收不到码时，回到家内网登录（物理内网即豁免），后台改绑手机。
3. **手机号在后台可改**（用户管理），改绑有 audit。
4. **Lucky/反代配置错误导致误判**：fail-safe 只会多要验证码，不会锁死内网。
5. 全局日发送上限（100 条）作保险丝，异常时停发而不是烧钱。

## 6. 风险

| 风险 | 应对 |
|---|---|
| 判定误伤（内网被判外网） | 只多一条短信不锁死；审计页可复核；`TRUSTED_PROXIES`/域名列表后台可调 |
| 判定漏放（外网被判内网）= 危险方向 | 双信号 + 「无法判定=外网」+ 公网 IP 默认外网；单测矩阵覆盖 |
| XFF 伪造绕过 | 可信代理白名单（顺带修复现有 `get_client_ip` 弱点） |
| 短信丢包/延迟 | 5 分钟 TTL + 可重发 + 发送/验证全审计 |
| 换手机号收不到码 | 内网豁免 + 后台改绑 |
| 短信费被恶意消耗 | 密码前置校验 + 三层限流 + 全局日上限 |
| 服务商审核不通过 | Provider 抽象可换；console 模式功能照常演示 |

## 7. 决策点（开工前请拍板）

| # | 问题 | 我的推荐 |
|---|---|---|
| D1 | 短信服务商选哪家？ | 先 console 联调；生产**榛子云**（门槛最低）。如已有腾讯云/阿里云账号则用之 |
| D2 | Tailscale / VPN 隧道（100.64.0.0/10）算内网还是外网？ | **算内网**（隧道本身有身份认证+加密）；不放心可配置成外网 |
| D3 | 已开 TOTP 的账号，外网时 TOTP 能否替代短信？ | **可以替代**（同级别第二因素，还省短信费） |
| D4 | 未绑手机号的账号，外网是否硬拒？ | **硬拒 + 提示联系管理员**（内网登录后台补绑）；不硬拒等于给外网留无第二因素的口子 |
| D5 | 当前外网通道已断（8443 现在是爱快路由器页面、Lucky 未运行）——要不要先恢复外网通道？走什么入口（爱快映射 8443→8090 / 重启 Lucky / DDNSTO / CF）？ | 恢复入口属部署项，与本功能开发并行；确定后把域名填进 `sms.external_domains` 即可 |

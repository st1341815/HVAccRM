# 开发报告：外网短信验证码登录（内外网自动识别）

- 项目：HVAccRM（暖通空调客户管理系统）
- 基线版本：v1.7.7（线上 healthy，2026-10-31 实测）
- 报告日期：2026-10-31
- 状态：**待评审**——文末有 5 个决策点需要拍板后开工

---

## 1. 需求

登录界面增加**短信验证码登录**，且该验证仅在检测到**外网访问**（外网域名或公网 IP）时启用；**内网环境登录体验保持现状**（账号 + 密码，不加任何步骤）。

一句话概括：**外网 = 密码 + 短信双因素；内网 = 现状，零变化。**

### 2.2 网络拓扑现状（2026-10-31 二次实测更新，外网通道已恢复）

**正式外网入口（13叔 2026-10-31 确认）：`https://crm.example.com:8443`**（原 `https://old.example.com:8443` 已弃用）。

```
外网用户 ──https──> 公网 8.8.4.4:8443 (iKuai 路由器 DNAT)
                        │
                        ▼
                Lucky @ 192.168.1.6:8443 （TLS 终结，*.example.com 泛证书，按 crm 子域反代）
                        │
                        ▼
                http://192.168.1.8:8090 → 容器 hvaccrm (v1.7.7 healthy)
```

实测矩阵（全部可复核）：

| 测试 | 结果 | 结论 |
|---|---|---|
| `https://crm.example.com:8443/login`（--resolve 直连真实 IP） | 200，HVAccRM 登录页，`ssl_verify=0` | 外网通道已恢复，泛证书有效 |
| DoH 查询 `crm.example.com` | → `8.8.4.4` | DNS 正常（本机 DNS 有 fake-ip 劫持，测外网须 `--resolve` 绕过） |
| `https://crm.example.com/`（443） | 404 `Lucky Warning` | 443 也在 Lucky，但无 CRM 规则；**入口只有 8443** |
| `https://old.example.com:8443/`（旧域名） | `iKuai OS V4` 路由器页 | 旧入口已废，与用户确认一致 |
| 经公网域名做一次错误登录，查容器日志 | `登录失败 user=nosuchuser_xtest ip=192.168.1.1` | **见下方「NAT 回流」关键发现** |
| 同上，但请求头塞伪造 `X-Forwarded-For: 8.8.4.4` | 日志仍记 `ip=192.168.1.1` | **Lucky 用真实客户端 IP 覆盖伪造 XFF（非追加），XFF 经公网不可伪造** ✓ |
| `audit_log` 历史外网登录 | `1.1.1.1`（10-14）、`9.9.9.9`（CF 段，10-18） | 历史链路 XFF 透传正常 |

**关键发现 1 —— Lucky 在传 XFF，且不可伪造**：应用收到的 TCP 直连源是 Lucky 所在的 `192.168.1.6`，而日志记到 `192.168.1.1`——该值只可能来自 XFF 头。伪造首段测试证明 Lucky 是**覆盖式**写 XFF（不是追加），所以经公网路径的 XFF 可信，**这是内外网判定的核心信号，已实证可行**。

**关键发现 2 —— NAT 回流（hairpin）边界场景**：测试机是内网设备（192.168.1.8 本机），经公网域名访问自己家宽带 IP 时，iKuai 做 NAT 回流把源地址 SNAT 成路由器自己（`192.168.1.1`）——**人在内网用域名访问时，应用看到的客户端 IP 是内网 IP**。真实外网用户则 XFF=其公网 IP，两者可区分。这引出决策点 D6：家里用域名访问算内网（IP 优先）还是外网（字面 Host 优先）——见第 7 节。NAT 回流的 `192.168.1.1` 无法被公网伪造（能完成 TCP 握手到达该地址的只可能是路由器自身的回流流量），按 IP 信号判内网是安全的。

**关键结论：**

1. 判定必须与入口产品解耦（Lucky 曾停摆、入口曾从 old.example.com 换到 crm.example.com——本次都赶上了），基于请求本身特征做通用判定。
2. XFF 链路已实证可用且不可伪造；判定算法在 XFF 采信上加**可信代理白名单**（`TRUSTED_PROXIES`）——防的不是 Lucky 这条路径（已证明干净），防的是「绕过 Lucky 直连 8090 伪造 XFF」的路径（纵深防御，8090 目前仅内网暴露，未来若映射公网则此白名单是唯一的伪造闸门）。

## 3. 方案设计

### 3.1 内外网判定：双信号模型（`app/net.py` 新模块）

到达 FastAPI 的请求，只有两组可信信号：

| 信号 | 内网取值 | 外网取值 | 说明 |
|---|---|---|---|
| **A. Host 头**（剥端口、小写归一） | 私网 IP（192.168.1.8 等） | 公网 IP，或命中配置的外网域名列表（`old.example.com` 等，支持 `*.example.com` 通配） | 用户心智模型里的「用什么地址访问」 |
| **B. 真实客户端 IP**（升级版 `get_client_ip`：仅当直连来源 ∈ 可信代理名单时才采信 XFF） | RFC1918 / 127.0.0.1 / 100.64.0.0/10（Tailscale，决策点 D2） | 公网 IP | 实际网络位置 |

**判定规则（IP 信号优先，fail-safe）：**

```
1. 解析「真实客户端 IP」：
   直连来源 ∈ TRUSTED_PROXIES（127.0.0.1、::1、172.16.0.0/12 容器网段、192.168.1.6 Lucky）
     → 采信 XFF 首段（Lucky 覆盖式写入，已实测不可伪造）
   否则 → XFF 一律不采信，真实 IP = 直连来源本身

2. 判定：
   真实 IP = 公网            → 外网
   真实 IP = 私网/回环/CGNAT  → 内网（含 NAT 回流的 192.168.1.1，见 2.2 关键发现 2）
   无法解析 → Host 兜底：Host ∈ 外网域名列表或公网 IP → 外网；仍判不出 → 外网（fail-safe）
```

- **IP 优先于 Host**：物理在内网（NAT 回流）就免短信；Host 信号只在 IP 不可用/不可判时兜底，以及作为日志辅助（两个信号都记录到 audit，便于复核判定依据）。
- **fail-safe**：判不出的请求一律按外网——宁可多发一条短信，不可漏放一次外网登录。
- 顺带修复现有弱点：`get_client_ip()` 目前无条件信任 XFF 首段（代码注释自认了这个弱点），本次升级为白名单感知版，审计与限速键同时受益。

**判定时机：GET /login 渲染时判一次（决定 UI 展示），POST /login 提交时再判一次（真正的执行点）**——不信任页面渲染时的状态，防止「内网开页、切外网提交」的边界，也防直接构造表单提交。

### 3.2 登录流程（外网）

```
① GET /login（判定=外网）
   └─ 渲染：账号 + 密码 + 短信验证码输入框 + [获取验证码] 按钮 + 提示「外网访问需短信验证」

② 点击 [获取验证码]（formaction 指向 /login/sms/send，账号密码随表单带上）
   ├─ 内网请求 ────────────→ 303 回登录页（提示：内网无需验证码）
   ├─ CSRF 失败 ──────────→ 400 页面过期
   ├─ 登录锁定中 ─────────→ 429 请等待 N 秒
   ├─ 账号不存在/停用/密码错 → 401「账号或密码错误」+ 计入现有失败锁定（不泄露用户名存在性）
   ├─ 账号未绑手机号 ─────→ 提示「该账号未绑定手机号，请联系管理员」（须先过密码，泄露面可接受）
   ├─ 60s 冷却 / 日限流 ──→ 提示稍后再试
   └─ 通过 ───────────────→ 生成 6 位码 → HMAC 哈希入库（TTL 5 分钟）
                             → 调短信服务商发送 → audit(sms_send)
                             → 303 回登录页，提示「验证码已发送至 139****5678」

③ 提交登录（POST /login，重新判定外网）
   密码校验 → 短信验证码校验（一次性、5 分钟内、错 3 次作废、错误计入失败锁定）→ 发会话 cookie → audit(login, auth_mode=sms)
```

**内网路径**：GET /login 判定内网 → 不渲染短信步骤；POST /login 判定内网 → 不校验 `sms_code`。**现有体验与代码行为完全不变。**

**设计要点：**

- **先验密码、后发短信**（而不是「输账号就发码」）：密码即第一道门，天然防短信轰炸（不向通过不了密码的人发短信）、防用户名枚举、省成本。
- **验证码与 user_id 绑定**：A 账号的码不能登 B 账号；两个账号绑同一手机号也不串。
- **验证码只存 HMAC-SHA256 哈希**（密钥用 `APP_SECRET_KEY` + 每条随机盐），不存明文——库文件/备份 zip 泄露也拿不到码。
- **与 TOTP 的关系**（决策点 D3）：推荐「开了 TOTP 的账号，TOTP 可替代短信」——同属第二因素（你拥有的东西），双验纯粹是负担还烧钱。默认实现为替代模式，代码上留一个开关。

### 3.5 短信服务商选型（决策点 D1）

| 方案 | 门槛 | 成本 | 集成工作量 | 建议 |
|---|---|---|---|---|
| **榛子云** | 个人注册即可、无需企业认证，充值即用，按条计费 | ~0.05 元/条 | HTTP + MD5 签名，urllib 约 30 行 | **个人自用首选** |
| 腾讯云短信 | 个人实名可申请，签名/模板报备审核 1–2 天 | ~0.045 元/条 | TC3-HMAC 签名，urllib 约 60 行 | 稳定，审核材料比阿里云松 |
| 阿里云短信 | 同上，个人签名审核最严（需与备案/应用名一致） | ~0.045 元/条 | V3 签名稍复杂 | 备选 |
| `console` provider | 无 | 0 | 验证码打进容器日志 | **开发联调必经阶段** |

推荐节奏：先用 `console` provider 完成开发与全流程自测并上线观察判定准确性 → 服务商账号下来后切换 `SMS_PROVIDER` + 填密钥 + 后台点「发送测试短信」→ 完整启用。**签名报备要提前 1–2 天去办**，不阻塞开发。

### 3.6 兜底与逃生通道（防「把自己锁外面」）

1. **后台总开关**（`sms.enabled`）：任何异常一键关掉整个功能，回到现状。
2. **内网永远免验证**：手机丢失/换号/收不到码时，回到家内网登录（物理内网即豁免），后台改绑手机。
3. **手机号在后台可改**（用户管理），改绑有 audit。
4. **Lucky/反代配置错误导致误判**：fail-safe 只会多要验证码，不会锁死内网。
5. 全局日发送上限（100 条）作保险丝，异常时停发而不是烧钱。

## 6. 风险

| 风险 | 应对 |
|---|---|
| 判定误伤（内网被判外网） | 只多一条短信不锁死；审计页可复核；`TRUSTED_PROXIES`/域名列表后台可调 |
| 判定漏放（外网被判内网）= 危险方向 | 双信号 + 「无法判定=外网」+ 公网 IP 默认外网；单测矩阵覆盖 |
| XFF 伪造绕过 | 可信代理白名单（顺带修复现有 `get_client_ip` 弱点） |
| 短信丢包/延迟 | 5 分钟 TTL + 可重发 + 发送/验证全审计 |
| 换手机号收不到码 | 内网豁免 + 后台改绑 |
| 短信费被恶意消耗 | 密码前置校验 + 三层限流 + 全局日上限 |
| 服务商审核不通过 | Provider 抽象可换；console 模式功能照常演示 |
